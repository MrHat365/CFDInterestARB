# 后台稳定性、低延迟与图表性能专项

日期：2026-10-15。交付范围：官方资料调研、源码修复与静态检查。用户禁止在macOS运行项目，因此没有启动应用、测试、MT5、基准程序或构建，也没有安装/升级依赖、连接实际账户、执行数据库迁移。以下性能收益是实现机制判断，不是实测结果。

## 结论与依赖决策

保留PySide6、NumPy、pyqtgraph与每账户独立worker。当前发现的问题有明确的代码原因，可以在不改变布局、配色、交互控件的条件下修复；本轮没有新增或替换第三方依赖。替换了图表内部的数据降采样方案，不依赖库的等间隔时间假设。

长期稳定运行不能由“使用新库”直接保证。现有瓶颈包括MT5同步API、账户级串行锁、历史对账、消息积压和绘图数据量。换图表不会缩短broker响应；换asyncio不会让同步MT5调用变成可取消的异步API。

## 已实施的修复

### 1. 图表数据量与不等间隔时间

原代码仅指定`peak`方式，未设置`auto=True`或有效`ds`；默认`autoDownsample=False`、`ds=1`，并未真正降采样。进一步核对pyqtgraph 0.13.7源码，自动降采样假设X等间隔，而当前曲线混合历史bar与实时tick。

最终实现`series_data.peak_envelope`：先按可视时间窗口切片，再按屏幕横向像素列分桶，选每桶真实最高/最低采样点，按原始时间排序，额外保留首尾点。输出最多`2×像素列数+2`个点；1000列视口最多2002点。这是源码可推导的绘制点数上限，不是帧率或延迟测试。原始缓冲最多20万点，统计、交易条件与十字光标使用完整数据。

图表保留现有颜色、线宽、阈值拖动、UTC时间轴、手动平移缩放与恢复跟随。调整窗口/尺寸后重算显示数据；关闭pyqtgraph再次降采样以避免改变选出的极值时间。短序列原样绘制。

绘图合并定时从250ms改为33ms。33ms是请求重绘前的合并间隔，**不是33ms端到端行情或交易延迟保证**。主线程忙时QTimer仍会晚触发；数据入口仍是约200ms轮询。

均值线从历史点数长度数组变为两个端点；SeriesBuffer已验证有限值，绘图不再重复分配有限值筛选数组。标量append直接校验，不再每个tick构造临时dict/list及两个NumPy数组。

### 2. 快照积压

EventQueue此前只在达到容量上限后替换旧快照。现改为入队时立即合并同事件、账户、generation的尚未消费快照。最新快照放在队尾，保留其与中间关键事件的先后关系。

行情/账户/持仓/订单列表/任务遥测可合并；交易回执和带request_id的任务确认不可合并。合并不表示删除交易任务。`dropped`包含主动合并的旧快照数，不能解释为丢单数量。行情是当前状态采样，系统仍不是逐tick无损行情档案。

### 3. 长期交易历史累积

`ManagedExecutor.snapshot`此前读取账户所有历史批次并解码JSON，再忽略已结束批次。现增加基于JSON状态的SQLite部分索引，只查询未关闭批次；历史仍完整保留，`batches()`默认仍返回全部记录供审计。

未知/缺失状态不会被当作关闭而排除。索引在账本初始化事务创建，首次对旧库建立索引会扫描历史一次；后续周期对账不再随已关闭历史数量线性增长。依赖SQLite JSON函数，Windows分发需验证。索引或损坏JSON导致初始化失败时会拒绝启用自动任务，不绕过账本。

没有降低受管订单意图的`FULL`持久化级别。活动批次的broker历史核验仍有成本，特别是大量同时持仓时；该优化不解决所有MT5锁竞争。

### 4. 表格刷新

自动任务面板复用已有QTableWidgetItem，只修改变化的文本，保留选中任务；不再每秒创建整表所有单元格对象。布局、列、格式与开关确认流程保持原设计。

### 5. 通信活着但执行停滞

新增WorkerHealth，在独立短锁内记录订单服务和行情轮询的进度，不获取MT5锁。ePong带进度年龄及健康状态：初始化允许120秒，服务启动后任一服务60秒未推进视为停滞。该检测证明循环是否推进，不代表每个交易条件、业务响应或broker执行成功。

独立IPC读线程收到ping时检查；停滞则先设置worker停止标志，父进程将会话置为FAILED并走既有有界停止流程。检查粒度受父进程心跳周期影响，不会精确在第60秒发生。若MT5调用持有GIL导致连ping也无法处理，父进程既有通信心跳超时负责发现失联。

不重发未知订单、不自动重启后恢复入场。正常但超过阈值的慢broker调用也会触发停止，Windows应结合真实调用分位数确认阈值。调用无法从Python安全中断，进程隔离用于最终收敛；终止期间的成交结果须通过账本和终端核对。独立IPC可识别失联，不意味着其他账户或所有持仓从此绝不会受外部故障影响。

### 6. 发送阻塞与退出排空

worker端也开启TCP_NODELAY；建立本地连接/首帧配置使用10秒socket超时。正常读取可长时间空闲，不给共享socket设置会误伤空闲读取的持续短超时。

增加独立发送监视线程，发送阶段超过10秒则停止worker并shutdown通道，打断阻塞sendall。结束时等待回执排空最多5秒，超时明确记录须核对账本，不再无限`Queue.join()`。日志会区分发送失败与排空超时；未发送回执不等于未成交。操作系统级失效仍需Windows故障注入验证。

## 第三方库比较与后续替换门槛

资料通过Context7和agent-reach的官方网页/官方仓库路径读取。下面的速度描述是库提供的机制或上游自述，不是本项目基准。

| 候选 | 官方资料核实结果 | 对当前项目的判断 |
| --- | --- | --- |
| pyqtgraph | NumPy数据、可视裁剪、降采样；自动降采样默认关，0.13.7实现假设等间隔 | 本轮保留渲染器，替换为保留真实时间的屏幕分桶数据适配器。最小迁移、现有交互不重写 |
| Qt Graphs | Qt Quick体系、2D/3D、平台图形后端；官网列GPLv3/商业许可 | 候选GPU渲染器。当前QWidget图需评估2D嵌入/PySide绑定及部署版本，重写阈值拖动/时间轴/光标并检查许可；不是改一行import |
| Qt Charts | 官方自Qt6.10起弃用，建议Qt Graphs | 不作为新的长期替代方案 |
| VisPy | 稳定路线为OpenGL；官网另列Datoviz/VisPy2实验方向 | 备选GPU图表，需Windows显卡、RDP、休眠恢复与上下文丢失验收；实验路线不直接替换交易终端 |
| Lightweight Charts | 专用交互金融图表，JavaScript库 | 适合Web金融界面；当前桌面嵌入需要WebEngine/JS桥、重做拖动参考线及注记；须满足上游许可/署名要求。不能保证总内存或跨进程延迟更低 |
| orjson | 输出UTF-8 bytes，支持Windows wheel；调用期间持有GIL，非有限数编码为null | 若IPC编码成为实测热点，是较小范围的替换候选；必须先明确非有限值、namedtuple、NumPy、整数边界与回执兼容契约。不能直接替换严格金融命令序列化 |
| msgspec | JSON/MessagePack、Struct、类型校验、无必需依赖 | 适合下一版有版本号的强类型IPC协议。迁移必须覆盖两端所有消息与异常语义；上游基准不等于本项目收益 |
| PyZMQ | 高水位、LINGER与显式消息传输；默认linger可无限等待 | 更适合多消费者/跨主机需求。不会自动提供持久化或业务exactly-once，亦不能消除MT5锁；当前每账户一条本地通道先修现有背压/超时 |
| uvloop | 官方setup.py明确拒绝Windows平台 | 不符合MT5 Windows部署条件 |

替换图表的实施门槛：在相同Windows机器/数据/窗口尺寸下，使用本轮显示裁剪与分桶后，仍出现由渲染器导致的不可接受卡顿或绘制故障，再实现Qt Graphs或VisPy同接口适配器；保留原外观与完整交互，逐项比较冷启动、RSS、p95/p99绘制耗时、拖动延迟、RDP兼容及连续运行结果。不能因“更新”直接判断更好。

替换IPC的实施门槛：先分离JSON编解码、排队、MT5锁等待、broker调用与绘图各段耗时；只有编码显著占用预算时才引入orjson或msgspec。若主要耗时在broker或历史查询，换编码器不会得到同等幅度的端到端收益。

## 尚未宣称完成的稳定性边界

- 当前后台指主程序存在时，关闭账户控制台仍由独立worker执行。退出整个应用会停止worker；不是Windows Service，也不承诺注销用户后继续交易。脱离桌面生命周期的服务化需另做会话/MT5终端所有权设计。
- MT5同步API仍由同账户锁串行访问。历史查询、账户对账或慢order_send会暂时阻塞同账户行情/任务；不能为性能让多个线程并发调用非线程安全API。
- AutomationEngine整次扫描仍有较长锁区间；活动持仓很多时历史核验量仍增长，下一步应在测量后分离只读估值与提交临界区，并在发单前再次核验风险、身份、行情与持仓。
- 父进程事件总线仍顺序处理数据库服务。极端磁盘/handler停滞会造成关键事件背压；本轮没有把全部DB操作搬到独立持久化服务，也没有取消EventEngine有序退出等待。
- 任务/意图有持久化和未知结果阻断，不是持续可用保证。停电、磁盘满、终端断线、API挂起时优先拒绝新增风险并保留核验线索。
- 当前依赖只有下限，尚无Windows验证过的锁文件/完整第三方许可清单。本轮未随意升级；生产发布必须在验收后固定版本和制品哈希。

## Windows待执行验收

1. 运行全部回归，再执行32任务、多账户、20万图表点的72小时观察；覆盖主窗口前后台、控制台开关、缩放/拖动、锁屏/RDP。记录RSS、线程/句柄数和SQLite/WAL增长，不能只看最后截图。
2. 图表：等间隔历史与密集不等间隔tick混合；尖峰、低谷、最后点的值/时间正确；大幅缩放、调整大小、长时间断流后恢复。检测原始数据不被显示降采样污染。
3. 排队：行情洪峰、慢GUI消费者、关键回执夹在快照中、不同账户/generation；确认合并计数可解释且关键回执/任务定义未被合并。
4. 执行停滞：分别挂起initialize、poll、orders，以及模拟“ping还能返回、order_send不返回”；确认出现FAILED、停止新增风险，重启开关仍暂停，未知结果不自动重发。
5. 传输：父进程不读回复、断开连接、退出时仍有回执；验证发送10秒/排空5秒限制及父进程最终清理。在途broker委托必须人工核对。
6. 旧库升级：复制测试库建立索引，验证open/blocked/missing状态均进入核验、closed仍可审计；用查询计划确认活动查询走部分索引。不得拿真实交易库做首次故障实验。
7. 分段采样p50/p95/p99：报价生成→worker读取、读取→决策、等待MT5锁、发单→回执、IPC编码/排队、GUI收到→绘制；用单调时钟度量同进程耗时，不混用broker时钟。33ms/200ms分别是配置间隔，不能作为这些结果。

建议验收目标（非已达成事实）：图表单次更新p95≤33ms、GUI交互p95≤100ms、无CPU饱和或持续内存/队列增长；broker调用单独报告。若这些目标在实际部署硬件不合理，依据分段数据调整，不能以删持久化/跳过核验换数字。
